> 一个合格代码审查agent,应该审查代码的什么

● 好问题。这是构建代码审查 agent 的起点——你得先知道"审什么"，才能设计 prompt 和工具。

  ---
  代码审查的六个维度

  一个合格的代码审查 agent，应该覆盖以下六个层次：

  1. 正确性（Correctness）—— 第一优先级

  审查代码是否真的做了它声称要做的事。

  - 逻辑错误：条件判断反了、循环边界差一（off-by-one）、布尔表达式写错
  - 类型错误：传参类型不对、None/null 未处理
  - 边界情况：空列表、空字符串、零值、极限输入时会不会崩
  - API 契约：函数签名和实际返回值是否一致

  2. 安全性（Security）—— 最容易被新手忽略

  审查代码是否有可被利用的漏洞。

  - 注入风险：SQL 注入、命令注入、XSS —— 用户输入没做参数化/Sanitize
  - 敏感信息泄露：密钥硬编码、日志里打印密码、报错信息暴露内部结构
  - 权限问题：缺少鉴权检查、越权访问
  - 依赖安全：用了已知有漏洞的第三方库版本

  3. 性能（Performance）—— 算法和资源

  审查代码是否浪费了不必要的计算或内存。

  - 算法复杂度：循环里嵌套了不必要的循环（N+1 query 问题）
  - 内存浪费：大文件全读入内存而不是流式处理、循环里不停创建大对象
  - 阻塞操作：同步等网络/IO 导致其他请求排队
  - 缓存缺失：重复计算相同的结果

  4. 可靠性（Reliability）—— 出问题时的行为

  审查代码在异常情况下会不会优雅处理。

  - 错误处理：try/except 范围太宽（裸 except）、吞掉了关键异常
  - 资源管理：文件句柄没关、数据库连接没还、锁没释放
  - 并发安全：竞态条件、死锁可能
  - 幂等性：重试会不会造成重复写入或扣款

  5. 可维护性（Maintainability）—— 给人看的

  审查代码过两个月还能不能看懂。

  - 命名：x、data、tmp 这种无意义变量名
  - 函数长度：一个函数干三件事，200 行不分拆
  - 重复代码：两处几乎一样的逻辑没有抽取
  - 耦合度：模块之间互相依赖得太死，改一处动全身
  - 注释质量：注释在说"做了什么"（代码已经说了），而不是"为什么这么做"

  6. 风格与规范（Style & Convention）—— 统一性

  审查代码是否遵循项目的约定和语言规范。

  - Python：PEP 8（命名、缩进、空行）
  - 项目级：团队自己的命名前缀、目录结构、import 排序规则
  - 一致性：就算选择了非主流风格，只要项目内统一就好

  对人类 reviewer vs 对 agent

  ┌──────────┬────────────────────┬────────────────────────────────┐
  │   维度   │      人类擅长      │           Agent 擅长           │
  ├──────────┼────────────────────┼────────────────────────────────┤
  │ 正确性   │ 理解业务意图       │ 发现模式性 bug                 │
  ├──────────┼────────────────────┼────────────────────────────────┤
  │ 安全性   │ 架构级漏洞         │ 系统性地逐条检查 OWASP 清单    │
  ├──────────┼────────────────────┼────────────────────────────────┤
  │ 性能     │ 架构瓶颈           │ 复杂度分析（O(n²) vs O(n)）    │
  ├──────────┼────────────────────┼────────────────────────────────┤
  │ 可靠性   │ 领域特定的异常处理 │ 系统性地检查边界条件           │
  ├──────────┼────────────────────┼────────────────────────────────┤
  │ 可维护性 │ 判断命名"好不好"   │ 检测函数长度、重复率等量化指标 │
  ├──────────┼────────────────────┼────────────────────────────────┤
  │ 风格     │ 会偷懒跳过         │ 不知疲倦地逐行检查             │
  └──────────┴────────────────────┴────────────────────────────────┘

  Agent 的优势是不会累、不会遗漏、能逐条对照清单。弱点是不理解业务上下文。所以好的代码审查 agent，设计思路是让 agent
  做它擅长的事——系统性的、模式化的检查，复杂业务判断留给人类。

  第二版：加入安全性（有成熟的检查清单可以套用）

  ---
  代码审查 Agent 的架构

  一个 agent 由三个核心部件组成，你学了 API 调用和工具调用，正好能对应上：

  ┌──────────────────────────────────────┐
  │          System Prompt               │
  │  定义角色、审查维度、输出格式       │
  ├──────────────────────────────────────┤
  │          Tools（工具）               │
  │  让 agent 能够读取文件、搜索代码    │
  ├──────────────────────────────────────┤
  │          Agent Loop                  │
  │  调用 API → 模型决定是否需要工具    │
  │  → 执行工具 → 把结果喂回模型 → 输出 │
  └──────────────────────────────────────┘

  一、工具设计

  Agent 需要"眼睛"才能看代码。至少需要 3 个工具：

  ┌─────────────┬────────────────────────────────────────┬───────────────────┐
  │    工具     │                  作用                  │       实现        │
  ├─────────────┼────────────────────────────────────────┼───────────────────┤
  │ read_file   │ 读取指定文件内容                       │ open() → 返回文本 │
  ├─────────────┼────────────────────────────────────────┼───────────────────┤
  │ search_code │ 在代码中搜索模式（函数调用、类定义等） │ grep / ast        │
  ├─────────────┼────────────────────────────────────────┼───────────────────┤
  │ run_command │ 运行 linter、测试等                    │ subprocess        │
  └─────────────┴────────────────────────────────────────┴───────────────────┘

  Python 审查可以加一个特色工具：

  ┌─────────────┬─────────────────────────────────────────────────────────┐
  │    工具     │                          作用                           │
  ├─────────────┼─────────────────────────────────────────────────────────┤
  │ ast_analyze │ 用 Python 的 AST 模块解析代码结构，提取函数、类、复杂度 │
  └─────────────┴─────────────────────────────────────────────────────────┘

  二、System Prompt 设计

  这是 agent 的灵魂。好的 prompt 要包含：
  1. 角色定义：你是谁，你的任务是审查 Python 代码
  2. 审查标准：检查哪些维度（正确性、可维护性）
  3. 输出格式：问题分级（严重/警告/建议）+ 具体位置 + 修复建议
  4. 行为约束：不要空泛评价，每条意见必须引用具体代码行

  三、审查流程

  用户输入「审查 xxx.py」
         ↓
  Agent 调用 read_file 读取代码
         ↓
  Agent 分析后输出审查报告
         ↓
  如果发现可疑点，Agent 可能调用 search_code 查找相关代码验证
         ↓
  输出最终报告

  2. 关闭终端后对话会消失吗？

  不会消失。 Claude Code 会自动保存对话历史。关闭终端后重新打开，在项目目录下运行 claude，用 /resume
  或上下箭头键可以选择恢复上一次对话。你也可以随时输入 /resume 来查看历史会话列表。

  有几种方式：

  - /resume：Claude Code 内置的会话恢复，直接接上上次的对话
  - /log：导出当前会话的完整记录到文件
